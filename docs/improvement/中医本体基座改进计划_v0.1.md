# 中医本体基座改进计划 v0.1

## 1. 文档定位

本文档用于整理当前项目作为“中医本体论基座”的后续改进计划。

当前项目已经具备本体基座雏形：Concept、Assertion、Evidence、Relation Schema、ConditionSet、Version、Projection 等关键对象已经出现，审核也已经开始消费本体查询结果。

但从严格的中医本体论基座角度看，当前系统仍存在三个核心问题：

1. `KnowledgeCard` 仍保留历史真相层痕迹，尚未完全降级为投影读模型。
2. 关系定义、术语归一、条件化断言、证据链路已经有结构，但还没有完全成为运行时强约束。
3. 阴阳五行、性味归经、君臣佐使、体质、时令、剂量等中医理论结构尚未充分成为一等公民。

本文档的目标不是重新设计一个新系统，而是在现有实现基础上，给出可分阶段落地的改进路线。

---

## 2. 总体目标

项目应逐步收敛到以下统一主链：

```text
Mention
-> NormalizationDecision
-> Concept
-> Assertion
-> ConditionSet
-> Evidence
-> Version
-> Projection
```

其中：

- `Mention` 表示文本中的原始提及。
- `NormalizationDecision` 表示从原始提及到标准概念的归一决策。
- `Concept` 表示中医知识世界中的稳定概念。
- `Assertion` 表示概念之间的知识命题。
- `ConditionSet` 表示断言成立的适用条件。
- `Evidence` 表示支撑断言的证据片段与来源。
- `Version` 表示本体结构、术语资源、知识内容的治理版本。
- `Projection` 表示面向审核、检索、RAG、前端展示的派生读模型。

审核、RAG、检索、前端知识卡等均应作为下游应用，只消费本体查询 API 或投影结果，不应反向决定本体结构。

---

## 3. 阶段一：冻结本体主链与术语边界

### 3.1 目标

先明确概念、提及、归一、断言、证据、投影之间的职责边界，避免后续开发继续混用 raw text、entity、concept、knowledge card、ontology fact 等对象。

### 3.2 改进内容

| 项目 | 改进内容 |
|---|---|
| 主链规范 | 固定 `Mention -> NormalizationDecision -> Concept -> Assertion -> Evidence -> Projection` |
| 命名规范 | 将运行时 `entities` 逐步改为 `concept_hits` 或 `ResolvedConceptHit` |
| 归一状态 | `NormalizationDecision.status` 扩展为 `resolved / ambiguous / unresolved / rejected` |
| API 契约 | 查询结果明确区分 raw text span、resolved concept、ontology fact、projection |
| Trace 结构 | 增加 `SemanticTrace`，串起 mention、normalization、assertion、evidence |

### 3.3 验收标准

1. 审核结果能回答“用户文本中的哪个 mention 被归一到了哪个 concept”。
2. 每条 ontology fact 都能追溯到 assertion、evidence、document、kb version。
3. `KnowledgeCard` 在文档和代码中只被描述为 projection/read model，不再作为本体真相层。
4. result detail API 能返回完整 semantic trace。

---

## 4. 阶段二：将 KnowledgeCard 彻底降级为投影

### 4.1 目标

消除“双真相源”。知识真相只来自 Concept、Assertion、Evidence、Condition，`KnowledgeCard` 只作为面向审核和前端的派生读模型。

### 4.2 改进内容

| 模块 | 改进内容 |
|---|---|
| 导入流程 | 导入只写 `ontology_entities`、`ontology_assertions`、`evidence_sources`、`condition_sets`、`concept_aliases` |
| 发布流程 | publish 后由 projection builder 生成 `knowledge_card_projections` |
| 查询服务 | 默认从 assertion 查询，不再 fallback 到 legacy `knowledge_cards` |
| 兼容层 | 保留 `KnowledgeCard` API，但明确标记为 read model |
| 重建能力 | 提供 projection rebuild 命令或服务方法 |

### 4.3 验收标准

1. 删除或禁用 legacy `knowledge_cards` 后，核心查询和审核仍能跑通。
2. `knowledge_card_projections` 可由 published assertions 完整重建。
3. 任意 projection 字段都能追溯到 assertion id。
4. 新导入版本不会直接污染 active projection，必须经过 publish。

---

## 5. 阶段三：统一关系 Schema 来源

### 5.1 目标

避免文档、代码常量、store 中的 relation definitions 逐渐漂移。关系定义应成为版本化、可治理、可校验的本体资产。

### 5.2 改进内容

| 项目 | 改进内容 |
|---|---|
| 单一注册表 | 以 versioned `RelationDefinition` 作为唯一来源 |
| Bootstrap | `DEFAULT_RELATION_SCHEMAS` 只用于初始化，不作为长期真相 |
| 导入校验 | 导入阶段使用同一 registry 做 domain/range/evidence_required 校验 |
| 查询约束 | 查询服务使用 relation registry 判断可查询路径和语义方向 |
| 文档同步 | 从 relation definitions 自动生成关系规范表，减少手工漂移 |

### 5.3 优先冻结的核心关系

```text
HAS_SYMPTOM
ASSOCIATED_WITH_PATTERN
HAS_PATHOGENESIS
BASED_ON_PATTERN
USES_METHOD
REALIZED_BY_FORMULA
HAS_INGREDIENT
HAS_FORMULA_ROLE
HAS_PROPERTY
ENTERS_MERIDIAN
SUITABLE_FOR_CONSTITUTION
SEASONAL_RELEVANCE
HAS_DOSE
SUBCLASS_OF
```

### 5.4 验收标准

1. 新增 assertion 时必须通过 domain/range 校验。
2. 未注册 relation 不能进入 published 状态。
3. 文档关系表、API 返回、导入校验结果一致。
4. legacy relation alias 必须通过 `canonical_relation_code` 映射为标准谓词。

---

## 6. 阶段四：将条件化断言变成运行时能力

### 6.1 目标

中医知识不能只靠简单三元组表达。系统需要支持“某个断言在特定证候、病机、体质、时令、剂量、人群、阶段下成立”。

### 6.2 重点能力

| 能力 | 示例 |
|---|---|
| 病机条件 | 脾虚证在“脾失健运”背景下关联某治法 |
| 体质条件 | 某方适用于阳虚体质，不适用于阴虚火旺 |
| 时令条件 | 某调理方法更适合冬季或长夏 |
| 剂量条件 | 小剂量调和，大剂量可能有风险 |
| 人群条件 | 孕妇、儿童、老人、哺乳期差异化约束 |
| 阶段条件 | 急性期、恢复期、慢性调理期适用关系不同 |

### 6.3 查询接口方向

建议逐步支持以下查询模式：

```text
query_assertions(
  subject,
  predicate,
  object,
  condition_context={
    pattern,
    pathogenesis,
    constitution,
    season,
    dose,
    population,
    stage
  }
)
```

### 6.4 验收标准

1. 查询“脾虚证”不会返回无关病机路径。
2. 查询“阳虚体质 + 冬季 + 某方”能返回条件匹配的断言。
3. 审核命中不只说明关系存在，还说明适用条件是否满足。
4. 不满足条件的断言不会被当作同等强度事实使用。

---

## 7. 阶段五：术语归一前移到知识治理层

### 7.1 目标

术语归一不应只是审核运行时日志，而应成为本体治理的一等能力。

### 7.2 改进内容

| 环节 | 改进内容 |
|---|---|
| 指南导入 | 抽取 mention、候选概念、归一决策 |
| 人工治理 | ambiguous/unresolved 进入 review 队列 |
| 别名管理 | `ConceptAlias` 绑定来源、版本、状态 |
| 审核运行时 | 只消费 published terminology resource，同时记录应用 trace |
| 纠错闭环 | 人工修正可反向沉淀为 terminology change record |

### 7.3 必须支持的归一场景

| 场景 | 要求 |
|---|---|
| 同义归一 | 孕妇、妊娠、孕期女性归一到同一 Population concept |
| 异名归一 | 黑附片、附片、附子需要区分别名与炮制品 |
| 语境消歧 | 阳虚在体质、证候、属性语境下可能对应不同 concept type |
| 近义区分 | 脾虚证与脾失健运不能混为同一概念 |
| 未解析提及 | 无法归一的 mention 应保留并进入治理队列 |

### 7.4 验收标准

1. 每个归一决策有 candidate list、confidence、rationale、review_status。
2. `NormalizationDecision` 支持 resolved、ambiguous、unresolved、rejected。
3. 应用侧审核不直接创建 published alias，只能提交候选变更。
4. 术语资源版本可独立发布，不必绑定知识内容版本。

---

## 8. 阶段六：提升中医理论结构为一等公民

### 8.1 目标

中医本体基座不能只表达“药材-功效-禁忌”。阴阳五行、性味归经、君臣佐使、体质、时令、剂量等理论结构必须进入核心模型。

### 8.2 优先补齐的对象

| 类型 | 建议建模 |
|---|---|
| 阴阳 | 作为稳定 `Property` 子类或独立 `YinYangProperty` |
| 五行 | 建立 `FiveElement`，支持生克乘侮关系 |
| 性味 | 建立 `NatureFlavor`，拆分四气、五味 |
| 归经 | 使用 `Meridian`，并关联脏腑/经络体系 |
| 君臣佐使 | 使用 `FormulaRole`，绑定方剂-药物-角色结构 |
| 体质 | 使用 `Constitution`，进入 ConditionSet |
| 时令 | 使用 `Season`，进入 ConditionSet |
| 剂量 | 使用 `Dose`，支持范围、单位、上下文 |

### 8.3 建模重点

1. `四君子汤 -> HAS_INGREDIENT -> 人参` 不够，还需要表达“人参在四君子汤中为君药”。
2. `甘草 -> HAS_PROPERTY -> 甘/平` 需要区分性、味、归经，而不是只作为普通属性。
3. 体质、时令、剂量应参与条件判断，而不是只用于前端展示。
4. 五行关系不应只是标签，应能表达生、克、乘、侮等关系。

### 8.4 验收标准

1. 方剂组成可查询到药物、角色、证据。
2. 单味药可查询到性、味、归经、适用体质和剂量条件。
3. 体质、时令、剂量可以参与 assertion condition matching。
4. 中医理论对象有独立定义、边界说明、正反例和版本。

---

## 9. 阶段七：建立本体回归测试集

### 9.1 目标

防止后续功能开发、导入逻辑调整、关系扩展把本体语义冲散。

### 9.2 黄金样本范围

| 场景 | 测试内容 |
|---|---|
| 病-症-证 | 消渴、口渴、阴虚证 |
| 证-病机 | 脾虚证、脾失健运 |
| 理法方药 | 补气、益气健脾法、四君子汤、人参 |
| 方剂角色 | 四君子汤中人参为君药 |
| 性味归经 | 人参性味、归经 |
| 条件禁忌 | 孕妇、儿童、长期服用、剂量限制 |
| 术语归一 | 别名、异名、近义但不同类 |
| 版本隔离 | draft 不影响 published 查询 |
| 证据追溯 | assertion 能追到 evidence、document、snapshot |

### 9.3 验收标准

1. 每次导入、发布、schema 变更都运行 ontology validation。
2. 每个核心 query path 有固定测试。
3. 回归测试能发现 relation drift、type mismatch、condition 丢失、evidence 丢失。
4. 黄金样本既覆盖审核场景，也覆盖纯本体查询场景。

---

## 10. 建议排期

| 迭代 | 重点 | 结果 |
|---|---|---|
| Sprint 1 | 主链规范、命名、KnowledgeCard 投影化方案 | 结构边界清晰 |
| Sprint 2 | Assertion-only query、projection builder、关系 registry 统一 | 真相源收敛 |
| Sprint 3 | Mention/Normalization 治理前移、真实 offset/context | 归一可审计 |
| Sprint 4 | ConditionSet 查询与运行时匹配 | 中医条件知识可执行 |
| Sprint 5 | 阴阳五行、性味归经、君臣佐使、体质时令剂量建模 | 中医理论结构升维 |
| Sprint 6 | 黄金样本、回归测试、发布治理 | 基座稳定可演进 |

---

## 11. 最高优先级任务

短期最值得先做三件事：

1. **KnowledgeCard 投影化**
   - 真相层只保留 Concept、Assertion、Evidence、Condition。
   - `knowledge_card_projections` 由 published assertions 重建。

2. **RelationDefinition 统一化**
   - 文档、代码、导入、查询共用一个关系 schema。
   - 新 assertion 必须通过 domain/range/evidence_required 校验。

3. **NormalizationDecision 治理化**
   - 将术语归一从审核运行日志前移到本体治理链路。
   - 支持 resolved、ambiguous、unresolved、rejected。

完成这三件事后，项目会从“审核应用驱动的知识图谱”进一步转向“中医本体基座驱动的多应用系统”。
