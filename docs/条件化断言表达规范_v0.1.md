# 《条件化断言表达规范 v0.1》

## 1. 文档定位

本文档用于定义“中医本体基座 v0.1”中的**条件化断言（Qualified Assertion）**表达规范，用以解决中医知识中大量“在某些条件下成立”的命题表达问题。

本文档目标是：

- 建立中医知识条件化表达的统一框架
- 避免将条件性知识错误扁平化为绝对三元组
- 为 assertion、证据、版本治理提供可操作的条件建模标准
- 使未来本体扩展建立在可治理的条件语义之上

本文档只讨论**条件化断言的表达规范**，不讨论下游审核、诊断、推荐等应用逻辑。

---

## 2. 为什么必须建立条件化断言

中医知识的一个根本特征是：

> **许多知识不是“无条件成立”的，而是“在特定证候、病机、人群、阶段、时令或语境下成立”的。**

例如：
- 某治法建立在某证候之上
- 某方剂适用于某类证候，而不适用于所有同名病
- 某病在某阶段可能表现某症，而在另一阶段未必如此
- 某药在特定条件下适宜，在另一条件下应慎用或不宜使用

如果不建立条件化断言机制，就会出现以下问题：

1. **知识扁平化**
   - 条件命题被误写成绝对命题

2. **知识失真**
   - 本体表达偏离中医实际知识结构

3. **关系膨胀**
   - 为了表达条件，关系名被无限细化

4. **治理困难**
   - 无法清晰区分“主命题”和“成立条件”

因此，v0.1 将“条件化断言”定义为本体基座的一等能力。

---

## 3. 术语定义

### 3.1 断言（Assertion）
表示一个基础知识命题，由主语、谓语、宾语构成。

示例：
- 四君子汤 `REALIZED_BY_FORMULA` 某治法（示意）
- 脾虚证 `HAS_SYMPTOM` 乏力

### 3.2 条件化断言（Qualified Assertion）
表示“基础知识命题 + 成立条件”的组合对象。

其本质是：

> **命题不是绝对成立，而是在条件集满足时成立。**

### 3.3 条件（Condition）
表示约束某断言成立范围的单个结构化前提。

### 3.4 条件集（ConditionSet）
表示由多个条件按照逻辑关系组合而成的结构化集合。

---

## 4. 条件化断言基本模型

v0.1 建议采用如下表达结构：

```text
QualifiedAssertion
= BaseAssertion + ConditionSet + Qualifier + Evidence
```

即每条知识至少分成四部分：

1. **BaseAssertion**
   - 主语、关系、宾语

2. **ConditionSet**
   - 该命题成立的前提集合

3. **Qualifier**
   - 命题强度、适用范围、说明性质

4. **Evidence**
   - 支撑该条件化命题的证据与来源

---

## 5. BaseAssertion 与 ConditionSet 的分工

### 5.1 BaseAssertion 负责什么
BaseAssertion 只负责表达命题主干：
- 谁和谁有什么关系

例如：
- 脾虚证 `HAS_SYMPTOM` 乏力
- 补气 `USES_METHOD` 益气健脾法

### 5.2 ConditionSet 负责什么
ConditionSet 负责表达命题在什么条件下成立，例如：
- 仅在某阶段
- 仅在某证候兼夹时
- 排除某类情况
- 只在某文献语境或范围内成立

### 5.3 分工原则
- **主命题不要写进条件**
- **条件不要写进关系名**
- **条件不要混入概念定义本身**

---

## 6. 条件的基本分类

v0.1 建议将条件至少划分为以下 7 类。

## 6.1 证候条件（Pattern Condition）
用于表达：
- 断言仅在某证候成立
- 断言建立在某辨证前提下

示例：
- 仅适用于气虚证
- 适用于痰湿证兼脾虚证

---

## 6.2 病机条件（Pathogenesis Condition）
用于表达：
- 断言仅在某病机背景下成立

示例：
- 仅在脾失健运时成立
- 适用于痰湿内阻之机

---

## 6.3 疾病条件（Disease Condition）
用于表达：
- 某命题仅在某病或病类语境下成立

示例：
- 在消渴病语境下
- 在咳嗽病范畴中

说明：
该类条件不应用于代替主语/宾语建模，而是在需要时缩小命题适用范围。

---

## 6.4 阶段条件（Stage Condition）
用于表达：
- 断言只在病程、治疗阶段、病势阶段中成立

示例：
- 初期
- 恢复期
- 急性发作期

说明：
阶段类对象在 v0.1 尚不要求完整扩展为核心类，但条件框架必须预留。

---

## 6.5 人群条件（Population Condition）
用于表达：
- 断言仅适用于特定人群或排除某些人群

示例：
- 适用于老年人
- 不适用于体弱者

说明：
`Population` 不在 8 大核心类之内，但条件表达框架需要支持其后续接入。

---

## 6.6 时令/环境条件（Temporal / Seasonal Condition）
用于表达：
- 断言仅在某季节、时令、环境背景下成立

示例：
- 冬令更宜
- 暑湿季节多见

说明：
此类条件在中医知识中重要，但在 v0.1 作为扩展条件类型预留。

---

## 6.7 排除条件（Exclusion Condition）
用于表达：
- 某命题在某些情况下不成立或不应直接泛化

示例：
- 非阴虚者不在此列
- 排除热证
- 无兼夹痰湿时不适用

说明：
排除条件非常重要，因为中医知识往往不是“只要满足 A 就成立”，还常常包含“若出现 B 则不成立”。

---

## 7. ConditionSet 的逻辑结构

### 7.1 单条件
最简单形式：

```json
{
  "all": [
    {"type": "pattern", "operator": "equals", "value": "气虚证"}
  ]
}
```

### 7.2 多条件且关系为 AND
示例：
“适用于脾虚证，且病机为脾失健运”

```json
{
  "all": [
    {"type": "pattern", "operator": "equals", "value": "脾虚证"},
    {"type": "pathogenesis", "operator": "equals", "value": "脾失健运"}
  ]
}
```

### 7.3 多条件且关系为 OR
示例：
“适用于气虚证或脾虚证”

```json
{
  "any": [
    {"type": "pattern", "operator": "equals", "value": "气虚证"},
    {"type": "pattern", "operator": "equals", "value": "脾虚证"}
  ]
}
```

### 7.4 含排除条件
示例：
“适用于气虚证，但排除热证”

```json
{
  "all": [
    {"type": "pattern", "operator": "equals", "value": "气虚证"}
  ],
  "not": [
    {"type": "pattern", "operator": "equals", "value": "热证"}
  ]
}
```

### 7.5 嵌套逻辑
v0.1 原则上允许嵌套，但不鼓励过早复杂化。

建议：
- 第一阶段优先支持 `all / any / not`
- 避免过度复杂的深层逻辑树

---

## 8. 条件表达字段规范

每个条件对象建议至少包含以下字段：

- `type`
- `operator`
- `value`
- `value_type`
- `normalized_concept_id`（如可归一）
- `scope_note`
- `source_note`

### 字段说明

#### `type`
条件类型，例如：
- `pattern`
- `pathogenesis`
- `disease`
- `population`
- `stage`
- `season`
- `exclusion`

#### `operator`
条件操作符，例如：
- `equals`
- `in`
- `not_equals`
- `includes`
- `excludes`

#### `value`
原始条件值或标准表达。

#### `value_type`
表示该值属于：
- `concept`
- `literal`
- `range`

#### `normalized_concept_id`
当条件值已归一为本体概念时，填写概念 ID。

#### `scope_note`
补充说明该条件适用边界。

#### `source_note`
保留原始文本或解析说明。

---

## 9. Qualifier 规范

条件化断言除了条件集，还应允许附加 qualifier，用于表达命题性质。

建议 qualifier 至少支持以下属性：

- `assertion_strength`
- `applicability`
- `certainty`
- `generality`
- `note`

### 9.1 assertion_strength
表示命题强度，例如：
- `strong`
- `moderate`
- `weak`

### 9.2 applicability
表示适用性质，例如：
- `applicable`
- `typically_applicable`
- `conditionally_applicable`
- `restricted`

### 9.3 certainty
表示确定性，例如：
- `high`
- `medium`
- `low`

### 9.4 generality
表示该命题的泛化程度，例如：
- `general`
- `specialized`
- `exception_case`

### 9.5 note
用于保留对条件强弱与边界的补充说明。

---

## 10. 条件化断言示例

## 10.1 示例一：证候条件

### 命题
益气健脾法适用于脾虚证。

### 表达
```json
{
  "base_assertion": {
    "subject": "益气健脾法",
    "predicate": "BASED_ON_PATTERN",
    "object": "脾虚证"
  },
  "condition_set": {
    "all": []
  },
  "qualifier": {
    "assertion_strength": "strong",
    "applicability": "applicable"
  }
}
```

说明：
该例条件为空，因为“脾虚证”本身已经是命题主对象。

---

## 10.2 示例二：附加病机条件

### 命题
健脾法建立在脾虚证背景下，尤其在脾失健运时成立。

### 表达
```json
{
  "base_assertion": {
    "subject": "健脾法",
    "predicate": "BASED_ON_PATTERN",
    "object": "脾虚证"
  },
  "condition_set": {
    "all": [
      {
        "type": "pathogenesis",
        "operator": "equals",
        "value": "脾失健运",
        "value_type": "concept"
      }
    ]
  },
  "qualifier": {
    "applicability": "conditionally_applicable",
    "note": "在脾失健运病机背景下更为典型"
  }
}
```

---

## 10.3 示例三：含排除条件

### 命题
补气法适用于气虚证，但不宜泛化到热证。

### 表达
```json
{
  "base_assertion": {
    "subject": "补气法",
    "predicate": "BASED_ON_PATTERN",
    "object": "气虚证"
  },
  "condition_set": {
    "not": [
      {
        "type": "pattern",
        "operator": "equals",
        "value": "热证",
        "value_type": "concept"
      }
    ]
  },
  "qualifier": {
    "applicability": "restricted",
    "note": "该命题不能脱离寒热属性直接泛化"
  }
}
```

---

## 10.4 示例四：多条件并列

### 命题
某治疗方法适用于气虚证，且多见于消渴病语境。

### 表达
```json
{
  "base_assertion": {
    "subject": "某治疗方法",
    "predicate": "BASED_ON_PATTERN",
    "object": "气虚证"
  },
  "condition_set": {
    "all": [
      {
        "type": "disease",
        "operator": "equals",
        "value": "消渴",
        "value_type": "concept"
      }
    ]
  },
  "qualifier": {
    "applicability": "conditionally_applicable",
    "generality": "specialized"
  }
}
```

## 11. 何时不应使用条件化断言

并非所有 assertion 都需要条件化。以下情况不应滥用条件：

### 11.1 当条件其实是主语/宾语本身定义的一部分
例如：
- “气虚证”本身已经是对象，不应再写一个“仅在气虚证时成立”的重复条件

### 11.2 当条件只是注释性修辞
例如：
- “一般来说”“通常”若不改变逻辑范围，可先进入 qualifier 而非条件集

### 11.3 当条件无法结构化且无治理价值
若条件只是模糊修辞，且暂时无法稳定结构化，不应硬塞成伪条件对象

---

## 12. 常见错误模式

## 12.1 把条件写进关系名
错误示例：
- `ONLY_FOR_QI_DEFICIENCY_PATTERN`
- `APPLICABLE_IN_WINTER_ONLY`

问题：
- 关系树膨胀
- 语义复用性差
- 无法治理

正确做法：
- 保持基础关系稳定
- 把差异写进条件集

---

## 12.2 把条件写进概念名
错误示例：
- “冬季脾虚证专用健脾法”直接作为概念

问题：
- 把临时条件凝固进概念
- 破坏概念稳定性

正确做法：
- 概念保持稳定
- 条件进入 assertion

---

## 12.3 把条件写成自由文本备注
错误示例：
- note: “适用于脾虚兼痰湿但不适用于热证且多见于秋冬”

问题：
- 机器不可解析
- 无法治理
- 无法查询

正确做法：
- 拆成结构化条件项

---

## 12.4 把条件和证据混在一起
错误示例：
- “据某指南，适用于脾虚证”写进 condition

问题：
- 来源与适用前提混淆

正确做法：
- 条件写适用前提
- 指南写进 evidence / source_document

---

## 13. 与证据层的关系

条件化断言不是脱离证据的抽象对象。

每条条件化断言原则上应支持：
- 来源文档
- 证据片段
- 支撑强度
- 条件解析说明

### 原则
- 证据支持的不是孤立三元组，而是“带条件的完整命题”
- 若证据只支持无条件部分，不应擅自补充未被支持的条件
- 若证据只在特定文献范围内成立，应通过 qualifier 标注泛化范围

---

## 14. 与版本治理的关系

条件化断言应纳入版本管理。

可能发生版本变化的内容包括：
- 主命题变化
- 条件变化
- 条件逻辑变化
- qualifier 变化
- 证据变化

### 原则
- 条件变化视为知识变更，不应被当作无影响的小注释改动
- 条件收紧或放宽都应可追踪

---

## 15. v0.1 推荐的最小实现形态

为避免一开始过度复杂，v0.1 建议至少支持：

### 15.1 条件逻辑容器
- `all`
- `any`
- `not`

### 15.2 条件类型
- `pattern`
- `pathogenesis`
- `disease`
- `population`
- `stage`
- `season`

### 15.3 条件操作符
- `equals`
- `in`
- `not_equals`

### 15.4 qualifier 基础字段
- `applicability`
- `assertion_strength`
- `note`

### 15.5 证据绑定
- `source_document`
- `evidence_refs`

这套最小实现已经足以支撑本体基座初期的条件治理。

## 17. 治理建议

### 17.1 条件录入时必须回答的问题
1. 该条件是否真的改变命题成立范围？
2. 该条件是否可结构化？
3. 该条件是否应属于主语/宾语定义的一部分？
4. 该条件是否有证据支持？
5. 该条件是否会影响断言的泛化范围？

### 17.2 审核优先级
建议优先审核以下条件：
- Pattern 条件
- Pathogenesis 条件
- Exclusion 条件

因为这三类最能体现中医知识的真实性与边界。

---

## 18. 结语

条件化断言不是对本体的装饰，而是中医本体基座能否成立的关键组成部分。

没有条件化能力，中医知识会被过度压扁；
条件表达失控，又会导致模型不可治理。

因此，v0.1 的核心目标不是追求复杂，而是建立一套：

- 可结构化
- 可解释
- 可治理
- 可扩展

的条件表达最小框架。

这一步完成后，本体基座才真正具备承载中医知识复杂性的能力。
